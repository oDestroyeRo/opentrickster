# Live action correlation on the pinned build

The planning goal is a macOS bot with the game visible inside the client-assisted app and a separate clientless dashboard controlling the same live character. The MVP covers combat and digging for one account and one character. Quest acceptance, completion, and turn-in remain manual. This report is a partial answer to [Verify live game sessions and action protocol](https://github.com/oDestroyeRo/opentrickster/issues/12), under [Plan the two-mode Trickster bot MVP](https://github.com/oDestroyeRo/opentrickster/issues/2).

**Result.** A fresh visual session reached the existing character and a ground click produced the expected outbound movement frame. A selected-point digging session produced outbound start and cancel opcodes, and the cancel payload differed from the inspected manual-cancel caller. No inbound position event was matched to the character, no basic attack was established as accepted, and no empty or found dig result was confirmed. The issue remains open. A visual client session does not establish a clientless connection, an embedded macOS game view, or authoritative state.

A fresh incognito preview tab ran the Unity client. Before login, a passive `WebSocket` wrapper copied binary views at send or receipt and retained them only in page memory. Text was retained only as direction and length. A temporary page file input loaded the owner's private credential delivery into memory. Synthetic keyboard events entered the fields; the page copy was then deleted. No packet was replayed or submitted directly. The account used one visual session and its existing character. No quest action, purchase, character creation, deletion, or other security change was made. The previously approved choice to decline the optional security lock was applied when the prompt returned.

The in-page decoder derived the public build's directional permutations and reassembled binary streams separately by socket and direction. It used the [six-byte gateway framing and seed derivation](https://github.com/oDestroyeRo/opentrickster/blob/331f397fe2d6440bc24b9ee51f9b7caa6100962b/docs/research/target-protocol-framing.md), not WebSocket message boundaries as packet boundaries. Its outbound movement and attack map entries agreed with `0xf36e` and `0x2fc9`. At the final read, no oversize declaration or pending binary suffix was observed. This is a limited runtime sanity check, not an independent proof of every map entry. The parent independently reproduced all four table hashes and inverses, the synthetic frame, fragmentation and coalescing, and size and seed rejection for this revision. The decoder reference records the full map fingerprints and executable derivation. A changed build invalidates these fixed wire values until its artifacts and maps are checked again.

The session included other actors and background traffic. No account or character identifier, authentication payload, session token, raw capture, or screenshot is included here. The in-page buffers were deleted and the tab was closed. No server-side release can be inferred from closing the tab.

## Static contracts and live limits

The pinned [compiled gateway and action reference](https://github.com/oDestroyeRo/opentrickster/blob/331f397fe2d6440bc24b9ee51f9b7caa6100962b/docs/research/target-protocol-framing.md) derives an LE `u16` payload length, LE `u16` wire opcode, LE `u16` Aux of unknown meaning, then payload. The maximum payload is 32745 bytes. Outbound maps logical opcodes through the build's c2s permutation; inbound applies the inverse s2c permutation. The reference also traces text controls, byte acknowledgements, and retained-byte resume and release paths. Those static paths do not establish server semantics or successful authentication and release.

The same reference traces ordinary monster `WorldClick` to logical `0x0120`, wire `0x1094`, with a `u16` target, followed by logical `0x001d`, wire `0x2fc9`, with a `u16` target and `u8` move mode. This is static extraction, not a live accepted attack in this session. The inspected manual `Drill.Press` and manual `Drill.Cancel` callers likewise do not prove the behavior of every automatic digging UI path. In particular, the observed nonzero cancel payload must not be replaced with the manual caller's zeros.

## Remaining evidence

1. Match one outgoing movement to an inbound event for the current character using a proven inbound handler and compare decoded position with the visible state. Distinguish the local character from surrounding actors and a movement request from a server correction or acceptance.
2. With an unclaimed target, capture the ordinary monster-click pair and correlate an inbound target or damage result to that character and target. Verify rejection, target loss, and cancellation before automating combat.
3. Trace the selected-point digging and separate automatic-spot callers and inbound handlers. Observe an actual empty or found result and any corresponding resource, inventory, and cancellation state. The stopped attempt above is not a completed outcome.
4. Check normal release and sequential reconnect after actions stop. This session closed the page without testing reconnect or server acceptance of release. No competing login or uncertain packet replay was attempted.
5. Separately prove a live authenticated native session with Unity absent, and separately show the game inside the macOS app. Neither follows from the browser test. Preserve manual quest acceptance, completion, and turn-in.

The smallest next prerequisite is the field-level inbound handler evidence being researched in [Recover incoming character and action-result message layouts](https://github.com/oDestroyeRo/opentrickster/issues/14). Then repeat one bounded movement correlation on the same fingerprinted build, keeping identifiers and authentication data private. The report does not claim that every server message or action path has been identified.
